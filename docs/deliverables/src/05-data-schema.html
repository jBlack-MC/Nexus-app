Server data model

server.js keeps four in-memory Maps, persisted as one JSON document { users: [...], projects: {userId: [...]}, tasks: {userId: [...]}, habits: {userId: [...]} }. Ownership is structural: every collection is keyed by the owner's user id, so there are no cross-user references {{F}}.

List columns are stored as Gson JSON strings by TaskConverters. userId is the cache owner id: the JWT sub, or a hash of the token if no sub exists. No foreign keys or indices are declared {{F}}.

Data flows

Principal data flows

DF-01Local writeViewModel → Repository → SyncManager.save() → Room entity + pending_changes (one transaction). See [[SEQ-01]].

DF-03RefreshGET /projects + GET /projects/:id/tasks for each project (N+1 requests) → replaces the account's cached projects and tasks → dashboard counts computed on the device
DF-04Account deletionDELETE /users/me → server removes the user and all collections → app purges that owner's Room rows and queue under the sync mutex
DF-05ExportHabits (cache or API) → CSV string in memory → Android share sheet. Nothing is written to shared storage.

Data retention and privacy notes

  • Personal data held: email, display name, password hash, and the user's own content. No analytics or third-party data processors are wired in {{F}}.
  • Retention: data is kept until the user deletes it or the account. There are no server-side backups or expiry {{F}}.
  • Logs: Pino redacts password fields, passwordHash, token and the authorization header. pino-http's default serializers do not log request bodies, so emails in bodies do not reach the logs, but remote IP addresses are logged {{F}}.
