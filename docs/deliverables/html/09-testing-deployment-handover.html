3Deployment summary

Full procedures are in NX-11-DEP; release gating is in REL-CHECK. In short: run the API with a persistent JWT_SECRET and persistent storage (Node host or backend/compose.yaml), put it behind HTTPS, and build the app with -PNEXUS_API_URL=https://…/api/. No environment beyond local development exists today (CON-02).

5Known limitations

  • Single-instance JSON store (CON-01); not suited to concurrent hosting or large data.
  • No background sync while the app process is stopped (CON-03).
  • Last-upload-wins for edits; no field-level merge (FR-17).
  • Reminders, push notifications, account recovery and collaboration are not implemented (NX-01-PRD scope).
  • Localisation is partial (FR-18).
  • Open defects: see NX-08-AUD.

6Runbooks

Operational runbooks
IDSituationSteps
RB-01API exits at start with "FATAL: JWT_SECRET is missing, too short…"Generate a secret: node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))". Set JWT_SECRET in the host's secret store (not in git) and restart. Reuse the same value on later restarts.
RB-02Health checkcurl -s https://<host>/health should return {"status":"ok","uptime":…}. Locally: http://localhost:5263/health.
RB-03All users suddenly see empty data after a restartLikely AUD-01. Stop the API immediately so no further writes occur. Inspect logs for "Failed to load database". Restore the data file from the latest backup (RB-04) and restart. Without a backup, the data overwritten by the empty store cannot be recovered.
RB-04Back up and restore data RecommendationBack up: stop the API, or accept a crash-consistent copy (writes are atomic renames), then copy nexus-data.json (container: docker compose cp api:/data/nexus-data.json ./backup-YYYYMMDD.json). Restore: stop the API, replace the file, start the API, check RB-02. Treat backups as personal data.
RB-05Users cannot sign in (HTTP 429)The limit is 10 auth requests per 15 minutes per IP, held in memory. Wait 15 minutes or restart the API. Behind a proxy, check AUD-06.
RB-06Rotate JWT_SECRETSet the new value and restart. Every existing session becomes invalid; users see "Sign in again to sync saved changes", and their queued changes upload after they sign in.
RB-07A user reports the sync banner stuck on "review required"Ask them to tap Review. "Discard item edits" removes only that item's queued edits, then the rest uploads. If they choose "Keep changes", nothing uploads until the conflict is resolved (AUD-19).
RB-08CI runs fail within secondsOpen the run with gh run view <id> and read the annotations. If they show "job was not started", the cause is an account or billing restriction, not the code (AUD-04).
